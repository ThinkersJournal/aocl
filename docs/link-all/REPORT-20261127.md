# Link-all over every `aocl-*-sys` crate against the installed AOCL 6.0.68 (Windows 11, x86_64), 2026-11-27

**Method** (`tools/link-all-crates.py`): for each crate and width, build it (bindgen as usual), take the address of EVERY `pub fn` of the bindings it generated in a throw-away test, and link. link.exe lists every unresolved symbol; each is classified against `dumpbin /exports` of EVERY AOCL DLL. **Controls in every row:** a made-up symbol must fail to link and be reported (negative; PASS everywhere); the same test minus the unresolved names must link (positive; PASS for every dynamic row; see static below). Data: `results-20261127.json.gz` (per row: declared, resolved, unresolved + class); the recorded known names: `known-unresolved.json.gz` (used by `--strict`). Measured only here: Windows, dynamic LP64 and ILP64, static LP64/ILP64 where it builds. **Linux is unmeasured.** No published crate was changed. The safe wrappers reference ZERO unresolved names (grep over `crates/aocl-<x>/src`; control: the same grep finds the resolved ones).

## Static (`static-link` feature)
- **blas:** the dynamic-unresolved `bli_*`/`lpgemm_*` RESOLVE statically (static-only symbols, as suspected): 5620 of 5704 declared resolve; the rest of the unresolved list is the OpenMP runtime (`__kmpc_*`) that the static lib needs and the crate does not link, so the **positive control fails** (the link needs libomp): the remaining 84 declared names are NOT yet classified.
- **lapack:** same 151 declared names unresolved as dynamic; 192 further unresolved are dependency symbols (`__kmpc_*`...): positive control fails (needs the OpenMP runtime).
- **fft, utils:** identical to dynamic (same unresolved sets; controls pass). **crypto:** all 89 declared resolve; 38 dependency symbols unresolved (BCrypt, OpenSSL `BN_*`/`EVP_*`: the static lib needs them linked): positive control fails. **data-analytics:** declared all resolve; link fails for another reason (no unresolved parsed; needs investigation).
- **sparse and compression: the `static-link` feature does not even build** on 6.0.68: the crates ask for `aoclsparse-static` / `aocl_compression-static`, the install has `lib/LP64/static/aoclsparse.lib` and `lib/static/aocl_compression.lib` (same base name as the import lib).

## What this does NOT say
Whether each name is "wrong" is for the owner: a name can be exported on Linux, by the static lib, or by a DLL the crate does not link. Remedies by class (PM defaults, 2026-11-27): not exported anywhere = default-OFF feature (never delete); exported by another DLL / only statically = link it behind a feature, measured; header-vs-binary mismatches = verify and gate. See ROADMAP rows 20-26.
