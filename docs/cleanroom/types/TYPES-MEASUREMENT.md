# ABI of types the AOCL guide uses but never defines: a behavioural MEASUREMENT

**Inputs used (only these):** (a) `guide-excerpts.txt` (AMD AOCL API Guide 6.0, doc 68552: LibM nexttoward and complex entries, RNG user-generator entries);
(b) the binaries `amd-libm\lib\libalm.dll`, `amd-rng\lib\LP64\rng_amd.dll`, `amd-rng\lib\ILP64\rng_amd.dll` and their `dumpbin -exports -dependents` output
(`dumpbin-libalm.txt`, `dumpbin-rng-LP64.txt`, `dumpbin-rng-ILP64.txt`); (c) the method of the earlier probes (`probe.rs`/`run.ps1`/`cargo-test.ps1`, `RNG-WIDTH-MEASUREMENT.md`, `SECRNG-MEASUREMENT.md`).
**No `.h` or other source file in the AOCL install was read (only the `lib\` directories were touched), no existing Rust binding, no prior knowledge of AMD headers. No disassembly of the DLLs.**
(Machine code was written only by us: a 12-byte `mov rax,imm64; jmp rax` trampoline in the exploratory `rng_probe.rs`, and `call` shims via `asm!` in `libm_probe.rs`.)
`ILP64` LibM: none exists (`amd-libm\lib` holds only `libalm.dll`, `libalm.lib`, `libalm-static.lib`); LibM has no integer-width issue.

**Machine:** AMD Ryzen 9 7940HX, Windows 11 Pro 10.0.26300, x86_64 MS x64 ABI, `rustc 1.100.0 (0ef1bc386 2026-11-09)`, `rustc --edition 2021 -O`.
**Libraries:** AOCL 6.0.68 install; RNG `"AOCL-RNG 6.0.0 Build 20261027"` (both builds; from RNG-WIDTH-MEASUREMENT.md). `libalm.dll` carries no version resource; no version string was read. Linux and the self-hosted rig were NOT measured.
**PATH** is set per child process (`run-libm.ps1`, `run-rng.ps1`: DLL dirs + `C:\Program Files (x86)\Intel\oneAPI\compiler\2026.1\bin`, ILP64 dirs first for ILP64); `KMP_DUPLICATE_LIB_OK` not set; no process was ever killed by image name.
`libalm.dll` depends only on `KERNEL32.dll`; the RNG DLLs' dependents are in the dumpbin files.

## DLL behaviour found while getting the user generator to run (important for any wrapper)

All with `lstate=100` unless noted; raw: `raw-rng-explore-lstate-and-smallstate.txt`, `raw-rng-*-init.txt`, `*-lquery.txt`, `*-gen_nopatch.txt`.
1. **`(s|d)randinitializeuser` always calls UINI first, regardless of `genid`** (genid -1, 0..13, 16, 20, 100 all did, exploratory `rng_probe.rs`), once per init.
2. **The DLL stores the UGEN code address into `state` as `[hi32, lo32]`: `state[0]=hi32(addr)`, `state[1]=lo32(addr)`, and ALSO `state[hi32+2]=lo32`.** For a normal code address (hi32 = 0x7ff6...) that is a **write at `state + 4*(0x7ff8)` = about 128 KB past the start of the state vector**, independent of `lstate`. With a 4096-slot state buffer this is an access violation (`0xC0000005`, fault offset `state+0x1ffe4`); with a 1,000,000-slot buffer it silently scribbles. Callbacks placed at addresses with a small hi32 (trampoline at 0x1_0000_0000) write `state[hi32+2]` close to the state start instead.
3. **A subsequent `(s|d)randuniform` on that state returns `info = -4` (parameter 4 illegal) and never calls UGEN** (`gen_nopatch`: UGEN_calls=0 in all four configurations). By experiment (hi32=1 trampoline, then a harness patch) the generation routine rebuilds the callback pointer as `(state[1] << 32) | state[2]` (the init wrote hi32 to slot 0 and lo32 to slot 1: shifted by one slot) and accepts the state only if `state[state[0]+2] == state[1]`. UGEN was reached ONLY after the harness set `state[0..4] = {1, hi32, lo32, hi32}` by hand after init (`gen`, `gen_wrongw`): that patch is a probe workaround, NOT a usage. So **on this build, on Windows x64, a user generator cannot be driven through the public API as documented** (the guide excerpts do not describe any other protocol).
4. `lstate = -1` with a UINI that writes `*lstate`: UINI sees `-4` (= -1-3); its write goes to a DLL local and is NOT copied back (caller's lstate stays -1, info 0). `lstate = 1` returns `info = -6` without calling UINI. `lstate` seems to need >= 3 + the user's state (header of 3 slots implied by `lstate-3`).

## Rust types and what stays undefined
`types_decls.rs` defines: `c_long_double = c_double`, `fc32_t`, `fc64_t` (+ `extern "C"` declarations of the eight LibM functions), `rng_int_t` (c_int / i64 under `ilp64`), the four callback typedefs (UINI D/S: 7 x `*mut rng_int_t`; UGEN D: `(.., *mut f64, ..)`; UGEN S: `(.., *mut f32, ..)`).
**Not defined / UNMEASURED:** any 5th+ UGEN argument; a working, safe call sequence for `srandinitializeuser`/`drandinitializeuser` (so those two entry points are not declared by this file: see item 2/3 above); any non-Windows ABI (on System V, `long double` is x87 80-bit and `fc64_t` is returned in xmm0:xmm1, but that was NOT measured and is NOT claimed).
`long double` / `c_double`: measured only for these two functions on this target; a wrapper must not reuse `c_double` for `long double` elsewhere without measuring.

## Controls that turned out vacuous (or partly)
- `nexttoward` f32-bits control for `y=0.5` (wrong and right both go down); `nt_ptrf64` (xmm1 unspecified, inconclusive).
- Swapped-field control for `cexpf(0+0i)` and `cexp(0+0i)` (symmetric input).
- `c32_ret_xmm0`: xmm0 low 32 bits equal `re` by DLL leftover (so "read xmm0" agrees with "read rax" for `re`); only the high half discriminates.
- LP64-vs-ILP64 "same answer" evidence is equality only, not a probe-power control; an int32 read of an 8-byte little-endian slot holding a small value is vacuous.
