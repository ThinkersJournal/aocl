## 0.2.27 - 2026-11-27 (PM-allocated; FIX aocl-crypto Rsa::set_private_key size and aocl-data-analytics kNN classes (safe-API memory safety, all published versions affected) + crypto and data-analytics wrapper tests; patch on 0.2.x)

- **`aocl-crypto` / `aocl-data-analytics`: result-checking tests for all 45 exposed wrapper functions no test mentioned** (crypto 24: NIST SP 800-38C CCM, McGrew-Viega GCM, RFC 8439 ChaCha20-Poly1305, RFC 7748 X25519, "abc" digests for all 12 modes, RSA OAEP/PSS/PKCS#1 v1.5/raw with tamper tests; data-analytics 21: reference computations and invariants), measured on AOCL 6.0.68 Windows (crypto 40 tests, data-analytics 44, 0 failed, 0 ignored).
- **Fixed, found by those tests (safe API):** `aocl_crypto::rsa::Rsa::set_private_key` passed the modulus size where AOCL 6.0.68 wants the size of each CRT component (half): the key size became twice the modulus and every private-key operation failed or overran the caller's buffer (heap corruption observed once); it now passes `p.len()`. `aocl_data_analytics::KNearestNeighbours::classes` passed the buffer length as the in/out count and returned it (garbage for an oversized buffer, access violation on an unfitted handle); it now returns the library's class count. Both existed in every published version (aocl-crypto 0.1.0 to 0.2.5; aocl-data-analytics 0.1.0 to 0.2.5). Four doc comments corrected (probability layouts are column-major, `digest_info_size` is the DigestInfo prefix length, the PKCS#1 v1.5 `random_pad` length, `sign_hash_pkcs1v15` takes DigestInfo || H). Also fixed (same class, safe API): `Aead::set_ccm_lengths` after `Aead::new` was accepted and did nothing (CCM tag stayed 12 bytes); it now returns `InvalidArgument` for an AES-CCM session, and the new `Aead::new_ccm(key, nonce, plaintext_len, tag_len)` declares the lengths in the order AOCL requires. `Handle::last_error_message` on a handle with no recorded failure could read uninitialised heap (AOCL returned success with a pointer to it, about 1 call in 25); it now reads the message only after a failure the wrapper has seen (the 16 internal error paths and the `Handle` option setters record one), so a fresh handle is always `None`. Concurrent RALFit solves crashed the process (access violation) when two threads used `Nlls` through the safe API; every NLLS library call (`new`, `fit`) now takes one process-wide lock, so concurrent fits run one after another (6 threads x 15 fits: crash before, 3 of 3 runs clean after). Found in review of #46 and fixed here: `Rsa::set_private_key` told the library every CRT component had `p.len()` bytes without checking the others, so a leading-zero-trimmed `dp` (63 bytes) next to a 64-byte `p` was an out-of-bounds read inside the call (access violation under a guard page before the fix); `dp`, `dq`, `p`, `q`, `qinv` must now be equal length and the modulus exactly twice that, else `InvalidArgument` before any FFI call. `Mode::default_tag_len` returned 16 for AES-CCM although AOCL 6.0.68 defaults to 12 (measured; the guide states no default): it now returns 12 for CCM. The NLLS lock now also covers `set_bounds`, `set_weights` and `info`, not only `new` and `fit`. Published versions affected: aocl-crypto 0.1.0 to 0.2.5 (`set_ccm_lengths`; `Rsa::set_private_key`), aocl-data-analytics 0.1.0 to 0.2.5 (`classes`, `last_error_message`, concurrent `Nlls`; read from each published `.crate`: no `error_pending` guard and no NLLS lock in any of 0.1.0, 0.2.2, 0.2.4, 0.2.5).
